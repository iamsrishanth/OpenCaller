# Voicemail and update security review

Reviewed 2026-11-22. Scope: SIP credentials, voicemail sync transport and storage, deletion behavior, live speech input, and the release/update metadata path.

## Controls reviewed

- SIP credentials and the voicemail sync bearer token are encrypted with an Android Keystore AES-GCM key. The server CA bundle is copied to app-private files, the app validates it for HTTPS and SIP TLS, and the app disables Android backup.
- The sync service is restricted to one configured Asterisk mailbox. It uses a constant-time bearer-token comparison, TLS 1.2 or newer, bounded metadata/audio reads, opaque SHA-256 message IDs, and does not log request paths or caller data. The example configuration says to keep it on a private LAN or VPN.
- The Android client rejects redirects for the mailbox service, validates the configured CA and hostname, checks the downloaded audio hash and size, stores message audio and transcripts in app-private files, and records deletion tombstones so a later sync does not restore a locally deleted item.
- Update checks read only the official GitHub Releases API and F-Droid display API. They compare numeric version codes; the F-Droid API is used for display only. Update links open only after a user tap. The app does not download or install packages, and cross-source upgrades remain disabled until signing compatibility is verified.
- Release metadata is read from the built APK's Gradle output metadata and contains only the application ID, version code, and version name.

## Findings and verification limits

- **Open, device-dependent speech input:** Android's `RecognizerIntent.EXTRA_AUDIO_SOURCE` documentation says a recognition service that does not support the extra may open the microphone instead. The app passes caller-only PCM through a pipe and keeps the SIP call microphone disconnected. The Moto G57 Power completed voicemail calls with transcription enabled, but its saved messages had no transcript. Live caller-audio recognition and microphone-source isolation therefore remain unverified on this handset. Live transcription is off by default, and the settings screen explains this behavior.
- **Android 17 local-network access:** Target SDK 37 requires the user to grant `ACCESS_LOCAL_NETWORK` before LAN SIP or mailbox traffic can reach a local server. The app now asks when the user connects the internet line or manually starts a voicemail sync. Background sync remains subject to Android's permission enforcement and retries if it cannot connect. This follows the [Android Developers local network permission guidance](https://developer.android.com/privacy-and-security/local-network-permission?hl=en).
- **Local deletion semantics:** Deleting a synchronized voicemail removes the phone's copy and retains a local tombstone to prevent it from being downloaded again. It does not erase the copy in Asterisk; the server copy can be deleted through the configured Asterisk voicemail tools. This is documented in the sync service guide.
- **Single mailbox service:** The companion HTTPS reader is intentionally scoped to one configured mailbox and bearer token. Operators who serve more than one user need a separate service instance and token for each mailbox; they should not share the token.
- **Cross-source signing:** Local same-source in-place installation succeeded with the existing signing certificate. A public GitHub release key and an F-Droid-signed package are not yet available to compare, so the app offers no cross-source package upgrade.
- **Public service exposure:** The LAN test server is reachable only on the local network used for testing. The service guide instructs operators not to expose port 8443 to the public internet. A public multi-tenant deployment has not been designed or reviewed.

## Current source status

On 2026-11-22, GitHub's latest stable-release API and F-Droid's official per-app API both returned HTTP 404. Both the API 37 emulator and Moto G57 Power displayed **No stable release yet** for GitHub and **Not listed yet** for F-Droid, with independent successful-check timestamps and daily checks off. The update fixture suite covers current versions, either source being ahead, an unlisted package, missing GitHub metadata, rate limiting, and one source being offline. A controlled Baresip call to Asterisk extension 1001, with no handset contact registered, created one new unread voicemail. Repeated authenticated HTTPS listing returned the same three IDs and the audio hash matched. The LAN sync endpoint returns HTTP 401 without a bearer token. A synthetic in-app voicemail survived an in-place Moto upgrade from version 0.1.4 to 0.1.5 and remained playable; its test fixture was removed afterward. On the emulator, the current source was installed as a test-only 0.1.6-test / 1007 update over 0.1.5 / 1006: first-install time stayed unchanged, all 12 voicemail WAV hashes matched, and a saved message played after the update. x86_64 emulator smoke checks also passed on API 26 and 34.

On API 37, a controlled incoming TLS/SRTP call reached the running app. The emulator showed an interim caller transcript, answered, and kept the same Asterisk call active while finalizing one message. A second test raced Answer with caller hangup; one item was saved and the call screen returned to its ready state. Neither emulator run produced the prior PJSIP callback crash. The emulator inbox played and sought a message, showed its transcript, and linked it to the matching recent call. Recipient-to-caller speech was not verified because the Baresip host has no working ALSA output. The PJSIP audio callback object is retained after detach until call media disconnects, and the last nonblank transcript is preserved through empty recognizer updates and caller hangup.

The 0.1.5 / 1006 build is installed on the Moto G57 Power (Android 17 / API 37), and the physical **Updates** screen has been checked. After Android's local-network permission was granted, the Moto registered to Zeus over SIP TLS and SRTP. During a controlled call from Baresip extension 1002, **Send to voicemail** opened the live voicemail screen. Tapping **Answer** returned to the active-call screen on the existing Baresip call; one 12.733-second local WAV was finalized. The player started, seeking moved playback to 6 seconds of 12, and its linked recent-call detail showed **Voicemail · listened**. The saved item had no transcript, so live recognition and microphone-source isolation are not verified on the Moto; recipient speech was not supplied or heard. The recording duration is consistent with the greeting and the first portion of the caller audio, ending before the second test phrase, but its contents were not independently transcribed. After permission was revoked for a UI check, the Voicemail **Sync** action showed Android's local-network permission prompt and the Allow action restored permission. Sync then failed because the phone-to-Zeus route was unavailable.

For the offline test, Wi-Fi and mobile data were disabled on the Moto before Baresip called extension 1001. Asterisk created one new `msg0002.wav` (191,724 bytes) in the mailbox at 18:01; FFprobe decoded it as an 11.98-second WAV. After the phone reconnected, the current Wi-Fi still could not reach Zeus at `192.168.0.14` from the phone, so the app line did not register and the physical inbox displayed a sync error. The server-side offline recording is verified; phone-side sync, duplicate suppression after that reconnection, and playback of that server message on the Moto remain unverified. A secure line, trusted CA, and mailbox token remain configured on the phone. No SIM carrier voicemail capability has been exposed because none has been verified with a carrier.
